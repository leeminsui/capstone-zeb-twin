# capstone-zeb-twin

충남대 공학 2호관을 3D로 세우고, 실측 2주치 운전 데이터를 그 위에서 재생하는 웹 페이지.

EEET 팀 과제 *「탄소중립 달성을 위한 EHP 기반 전기화 건물의 P2H-EMS 최적화 기술」*의
시연용. 2026-09-29 ~ 10-12 구간에서 PV 발전 예측과 EHP 냉방 제어가 15분마다 어떻게
맞물리는지 보여준다. 서버도 네트워크도 필요 없다 — `index.html` 하나를 열면 바로 돈다.

**보기:** https://leeminsui.github.io/capstone-zeb-twin/

## 화면

ㄷ자 중정형 4층 본관에 E2 타워, 옥상 PV 어레이, 실외기. 우측 윙은 중정 쪽 벽을 떼어낸
커터웨이라 층별 실내와 실내기·급기 흐름이 보인다.

**챕터 세 개** — 버튼 또는 숫자키 `1` `2` `3`. 한 번에 한 가지만 보여주려고 나눴다.

| | 보는 것 | 카메라 |
|---|---|---|
| 1 · 예측 | 옥상 PV 어레이 + 6시간 예측 차트 | 지붕 위 |
| 2 · 제어 | 사무실 단면 — **2D 화면으로 전환** | 3D가 아님 |
| 3 · 종합 | 발전·수전 흐름, 캠퍼스 전경 | 멀리서 |

**예측 차트** (챕터 1)가 이 페이지의 핵심이다. `now` 왼쪽은 실측 궤적, 오른쪽은
Transformer가 내놓은 6시간(lead 1~24) 예측. 옅은 선 두 개는 1시간·2시간 전에 내놓았던
예측이라, 15분마다 호라이즌이 갱신되며 밀리는 모습이 겹쳐 보인다 — MPC가 쓰는
receding horizon 그 자체다.

**실내 뷰** (챕터 2)는 3D가 아니다. 제어를 누르면 3D 장면이 축소되며 사라지고
사무실 단면 일러스트로 화면이 통째로 전환된다. 좁은 3D 실내를 돌아다니는 것보다
한눈에 읽히기 때문이다. Canvas 2D로 매 프레임 그린다.

커튼월 너머로 날씨와 시각이 그대로 보이고, 천장 카세트에서 찬 공기(또는 더운 공기)가
`p_cooling_kw`에 비례한 농도로 쏟아진다. 실내 공기는 쾌적밴드를 벗어난 만큼 푸르거나
붉게 물든다. 재실자는 업무시간(08:00~19:30)에만 앉아 타자를 치고, 두 명이 복도를
오간다. 밤에는 조명이 꺼지고 사무실이 빈다. 축척은 실 높이 3.1 m를 기준으로 잡아
화면 크기에 따라 보이는 실 길이가 달라진다.

**엔진 패널**은 15분 주기 안에서 기상 수집 → PV 예측 → MPC 최적화 → 첫 입력 적용 →
EHP 운전 다섯 단계가 순차로 점등된다.

| 보이는 것 | 연결된 값 |
|---|---|
| 하늘·해 위치 | 재생 시각 |
| 옥상 패널 밝기 | `pvs` (건물 규모 발전) · 출력제한 시 붉은 기운 |
| 실내 공기 색 | `rt`가 쾌적밴드 `cl`~`ch` 안인지 (파랑 하한 / 초록 정상 / 주황 상한) |
| 실외기 팬·급기 입자 | `mode`, 속도와 농도는 `pc` |
| 하늘색·구름·그림자 | `cc` (복원한 구름량) — 흐리면 그림자가 사라지고 하늘이 회색으로 |
| 초록 입자 | PV → 건물 |
| 주황 입자 | 계통 → 건물, `gi` |

하단 타임라인은 14일 전체. 초록 면적이 발전, 주황 선이 수전, 파란 눈금이 냉방 구간.
클릭하면 그 시각으로 이동한다. 스페이스바 재생/정지, 좌우 화살표로 한 시간씩.

## 구조

```
index.html              페이지 전체 (CSS·JS 인라인, 외부 의존은 Three.js뿐)
data/zeb_window.js      재생 데이터 — window.ZEB_DATA 로 주입
scripts/export_window.py  서버 DB에서 위 파일을 다시 만드는 스크립트
```

데이터를 `.js`로 두는 이유는 `fetch` 없이 `<script src>`로 읽히기 때문이다.
그래야 GitHub Pages에서도, 파일을 그냥 더블클릭해도 똑같이 돈다.

Three.js r128을 cdnjs에서 불러온다. 인터넷이 막힌 데서 띄울 거면 `three.min.js`를
받아서 옆에 두고 `<script src>` 경로만 바꾸면 된다.

## 데이터 다시 뽑기

| DB | 테이블 | 쓰는 값 |
|---|---|---|
| `ehp_control_log.db` | `mpc_control_log_adv` | 실내·외기 온도, 냉난방 전력, 부하, 수전, 요금, 쾌적밴드 |
| `pv_forecast_for_ehp_control.db` | `pv_forecast_24step` | PV 예측 (lead 1~24 = 15분~6시간 앞) |
| `pv_mppt_data_v2.db` | `pv_data` | MPPT 실측 전력·일사량·패널온도 |
| `room_temperature.db` | `readings` | DS18B20 실내온도 실측 |

## 읽을 때 주의할 점

**`pvs`는 실측이 아니다.** MPC가 쓰는 `pv_kw`는 대전 소형 패널의 예측값(W)을
3600배 스케일해 1 MW급 가상 건물에 맞춘 값이다. 전 구간에서 비율이 3596~3603으로
일정한 것을 확인했다. 실제 측정된 발전량은 `meas`(W, 패널 원단위)이고, 예측은
`fc`(W)다. 발표 자료에 올릴 때 이 구분을 빼면 질문을 받는다.

**예측 모델이 구간 밖에서 교체됐다.** 2026-10-20 14:00부터 `model_path`가
`donghyeon_hybrid_daejeon15:3seeds`로 바뀐다. 현재 재생 구간(9/29~10/12)은 전부
이전 모델이라 섞이지 않는다. 구간을 뒤로 옮길 때는 이 경계를 넘는지 확인할 것.

**실측 PV가 2026-10-13부터 멈춰 있다.** 샘플은 하루 17,000개씩 정상으로 들어오는데
전력만 0.3~0.6 W다. 통신이 아니라 패널·ELTO 전자부하·MPPT 추종 쪽 문제로 보인다.
10/16~10/17만 잠깐 복귀했다. 재생 구간을 9/29~10/12로 잡은 이유가 이것이다.

## 날씨 복원

장면의 날씨는 꾸민 것이 아니라 Solcast 관측에서 되살린 것이다. 확산광 비율
`dhi/ghi`로 구름량을 계산한다 — 맑으면 0.18 근처, 완전히 흐리면 1.0에 가까워진다.
이 값을 0~1로 정규화해 하늘 색, 해의 가시성, 직달광 세기, 그림자 유무에 연결했다.
야간 구간은 양옆 낮값을 선형 보간한다.

구간 내 일평균 구름량: 10/03이 0.87로 가장 흐렸고, 10/02가 0.29로 가장 맑았다.
페이지는 10/02 정오에서 시작한다.

외기온도는 MPC 로그의 `outdoor_temp_c`가 정수로 반올림돼 있어, 화면에는 Solcast
`air_temp`를 쓴다.

## 과제 문서와 다른 점

과제계획서에는 PV 예측 모델이 **CNN-LSTM 하이브리드**로 적혀 있으나, 실제 운영
파이프라인은 **Transformer**로 교체되었다(`donghyeon_hybrid_daejeon15:3seeds`).
화면 표기는 실제 운영 중인 모델을 따른다.
