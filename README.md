# capstone-zeb-twin

충남대 공학 2호관의 실측 2주치 운전 데이터를 감시제어 화면으로 재생하는 웹 페이지.

EEET 팀 과제 *「탄소중립 달성을 위한 EHP 기반 전기화 건물의 P2H-EMS 최적화 기술」*의
시연용. 2026-09-29 ~ 10-12 구간에서 PV 발전 예측과 EHP 냉방 제어가 15분마다 어떻게
맞물리는지 보여준다. 서버도 네트워크도 필요 없다. `index.html`을 열면 바로 돈다.

**보기:** https://leeminsui.github.io/capstone-zeb-twin/

## 화면

한전 감시제어(SCADA) 화면의 문법을 따른다. 어두운 바탕, 1px 테두리 패널, 상태 램프,
계측값 표, 이벤트 기록. 왼쪽에서 화면을 고르고, 가운데가 그 화면, 오른쪽이 지금 값이다.
가운데 맨 위 한 줄이 지금 무슨 일이 일어나는지 문장으로 말한다.

| 키 | 화면 | 보는 것 |
|---|---|---|
| `1` | 발전 예측 | 공학 2호관 3D(옥상 패널, 날씨)와 6시간 예측 차트 |
| `2` | 실내 제어 | 사무실 단면 3D(천장 EHP 세 대, 재실자)와 24시간 실내온도 추이 |
| `3` | 알고리즘 | 예측 모델과 EHP 제어가 15분마다 맞물리는 구조도 |
| `4` | 실험 결과 | 14일 전체 집계. 예측 정확도와 제어 성능 |

**발전 예측.** 차트의 흰 선이 실측, 주황 선이 방금 내놓은 6시간 예측이다. 점선 두 개는
1시간 전과 2시간 전에 내놓았던 예측이라, 15분마다 예측이 다시 계산되며 밀리는 모습이 보인다.

**실내 제어.** EHP가 돌면 천장 카세트에서 기류가 내려오고 태그에 소비전력이 뜬다. 재실자는
업무시간(08:00~19:30)에만 있다. 실내온도가 쾌적 범위를 벗어나면 계측값 표에 "주의"가 뜬다.

**알고리즘.** 구조도의 상자와 문구는 `js/view-algo.js`의 `ZEB.algoSpec`에서 읽는다.
**지금 내용은 추정이다.** 화면 제목 옆에도 그렇게 적혀 있다. 코드를 확인해 내용을 고친 뒤
`confirmed: true`로 바꾸면 표시가 사라진다. 강화학습 제어기는 "예정" 탭으로만 있다.
"6시간 운전 계획" 칸은 MPC가 세운 계획이 아니라 이후 6시간의 실제 운전 기록이다.

**실험 결과.** 숫자는 전부 `data/zeb_window.js`에서 계산한다(`ZEB.data.results()`).
업무시간 쾌적 범위 유지율은 숨겨 두었다. `js/data.js`의 `ZEB.config.showComfort`를
`true`로 바꾸면 나온다.

### 조작

| 키 | 동작 |
|---|---|
| `1` `2` `3` `4` | 화면 전환 |
| `Space` | 재생, 일시정지 |
| `←` `→` | 1시간 이동. `Shift`와 함께 누르면 하루 |
| `[` `]` | 재생 속도 (15분, 1시간, 4시간, 12시간 / 초) |
| `Home` | 10/02 12:00로 |

아래 타임라인을 누르면 그 시각으로 간다. 60초 동안 입력이 없으면 화면이 30초마다 자동으로
넘어가고, 아무 키나 누르면 멈춘다. 가로 1280px보다 좁은 화면에서는 안내문만 나온다.

주소 뒤에 `?view=3&i=337&paused=1`처럼 붙이면 화면, 시각(15분 단위 번호), 정지 상태를
정해서 열 수 있다.

## 구조

```
index.html               틀 (상단 바, 메뉴, 계측값, 타임라인)
css/app.css              색, 글꼴, 패널
js/data.js               ZEB.data — 시각별 값, 이벤트, 14일 집계
js/shell.js              ZEB.shell — 재생, 키, 화면 전환, 자동 순환
js/chart.js              추이 차트 (캔버스)
js/scene-exterior.js     건물 3D
js/scene-room.js         사무실 3D
js/view-*.js             화면 네 개
data/zeb_window.js       재생 데이터 — window.ZEB_DATA
vendor/                  Three.js r128, Pretendard (둘 다 저장소에 들어 있다)
scripts/export_window.py 서버 DB에서 재생 데이터를 다시 만드는 스크립트
tests/                   자동 검사
```

빌드 과정이 없다. 외부 요청도 없다. 인터넷이 끊긴 곳에서 `index.html`을 더블클릭해도
GitHub Pages와 똑같이 돈다. 데이터를 `.js`로 두는 이유도 `fetch` 없이 읽기 위해서다.

## 읽을 때 주의할 점

**`pvs`는 실측이 아니다.** MPC가 쓰는 `pv_kw`는 대전 소형 패널의 예측값(W)을
3600배 스케일해 1 MW급 가상 건물에 맞춘 값이다. 전 구간에서 비율이 3596~3603으로
일정한 것을 확인했다. 실제 측정된 발전량은 `meas`(W, 패널 원단위)이고, 예측은
`fc`(W)다. 발표 자료에 올릴 때 이 구분을 빼면 질문을 받는다.

**재생 구간의 예측은 예전 모델이 낸 것이다.** 2026-10-20 14:00부터 `model_path`가
`donghyeon_hybrid_daejeon15:3seeds`로 바뀐다. 재생 구간(9/29~10/12)은 전부 그 이전 모델의
예측이다. 그래서 화면에는 모델 이름을 적지 않고 "예측 모델"이라고만 쓴다. 알고리즘 화면의
구조도는 지금 운영 중인 모델을 추정해 그린 것이므로, 재생되는 숫자와 구조도가 같은 모델의
것이 아닐 수 있다. 구간을 뒤로 옮길 때는 이 경계를 넘는지 확인할 것.

**실측 PV가 2026-10-13부터 멈춰 있다.** 샘플은 하루 17,000개씩 정상으로 들어오는데
전력만 0.3~0.6 W다. 통신이 아니라 패널·ELTO 전자부하·MPPT 추종 쪽 문제로 보인다.
10/16~10/17만 잠깐 복귀했다. 재생 구간을 9/29~10/12로 잡은 이유가 이것이다.

## 실험 결과 (2026-09-29 ~ 10-12, 1,344스텝)

**PV 발전량 예측** — 전 구간 1,344스텝 기준

| | |
|---|---|
| MAE / RMSE | 3.95 W / 8.49 W |
| nMAE / nRMSE | 5.8 % / 12.4 % (용량 68.2 W 기준) |
| R² | 0.854 |
| 편향 | **-2.38 W** — 모델이 실측보다 일관되게 높게 예측 |

야간 696스텝(전체의 52 %)은 예측·실측이 모두 0에 가까워 오차가 거의 없다.
낮시간 648스텝만 떼면 MAE 8.14 W, RMSE 12.23 W, nMAE 11.9 %, R² 0.744다.
레짐별 분해는 낮시간 기준이다.

하늘 상태별로 나누면 편향의 정체가 드러난다.

| 레짐 | 스텝 | MAE | 편향 |
|---|---|---|---|
| 맑음 (cc<0.35) | 387 | 8.73 W | **-6.72 W** |
| 보통 | 109 | 7.88 W | -5.26 W |
| 흐림 (cc≥0.7) | 152 | 6.81 W | -0.16 W |

맑은 날일수록 과대예측이 심하고, 흐린 날은 편향이 거의 0이다. 당진 모델의
clear-sky 과대예측 경향([[pv-forecasting-capstone]]의 Phase 0 진단)이 대전 패널에서도
같은 방향으로 남아 있다.

**EHP 제어** — 14일 누적

| | |
|---|---|
| PV 발전 / 건물 부하 / 계통 수전 | 19,909 / 64,839 / 50,824 kWh |
| 자가소비율 | 70.4 % |
| 에너지자립률 | 21.6 % |
| EHP 냉방 | 6,281 kWh (부하의 9.7 %) |
| 전기요금 | 1,531,834 원 (일평균 109,417 원) |
| 냉방 운전 | 370 / 1,344 스텝 (27.5 %) |

PV 연계가 잘 동작한다. 냉방 운전의 **94 %(346/370스텝)가 PV 발전 구간**에 몰려 있고,
평균 냉방단가 101.3 원/kWh로 전체 평균 104.8 원/kWh보다 낮다. 고가 시간대(>150원)
냉방은 0스텝이다.

**쾌적도는 시간대를 나눠 봐야 한다.** 전 구간 기준 준수율은 18.3 %지만, 이탈의 대부분이
야간이다.

| 구간 | 준수율 | 평균 이탈 |
|---|---|---|
| 업무시간 08–20 | 36.3 % | 0.28 °C |
| 야간·비재실 | 0.3 % | 0.81 °C |

야간 이탈은 재실자가 없어 냉방을 정지한 결과이므로 설계 의도에 맞다. 다만 업무시간
준수율 36 %도 낮은 편이고 상한 초과가 100 %(하한 미달 0스텝)라, 밴드를 넘겨도 되는
허용폭(slack)이 느슨하게 잡혀 있을 가능성이 있다. 확인이 필요한 항목이다.

## 날씨 복원

장면의 날씨는 꾸민 것이 아니라 Solcast 관측에서 되살린 것이다. 확산광 비율
`dhi/ghi`로 구름량을 계산한다 — 맑으면 0.18 근처, 완전히 흐리면 1.0에 가까워진다.
이 값을 0~1로 정규화해 하늘 색, 해의 가시성, 직달광 세기, 그림자 유무에 연결했다.
야간 구간은 양옆 낮값을 선형 보간한다.

구간 내 일평균 구름량: 10/03이 0.87로 가장 흐렸고, 10/02가 0.29로 가장 맑았다.
페이지는 10/02 정오에서 시작한다.

외기온도는 MPC 로그의 `outdoor_temp_c`가 정수로 반올림돼 있어, 화면에는 Solcast
`air_temp`를 쓴다.

## 과제 문서와 다른 점

과제계획서에는 PV 예측 모델이 **CNN-LSTM 하이브리드**로 적혀 있으나, 운영 파이프라인의
모델은 그 뒤 교체되었다(`donghyeon_hybrid_daejeon15:3seeds`). 새 모델의 구조는 코드로
확인하지 못했다. 확인 전까지 화면과 이 문서는 "예측 모델"이라고만 쓴다.
